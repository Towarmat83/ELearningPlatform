E-Learning Platform · Hands-on Labs

Lab Checker — Design

A generic, declarative way for the e-learning platform to verify that a learner actually performed a hands-on lab against a real backend (GitLab, Harbor, Nexus, …) — "create a PAT", "push a commit", "open a merge request", "push an image", "create a raw hosted repo" — and return per-assertion, teaching-oriented feedback rather than a bare pass/fail.

1. Core insight: the check is the quiz

The platform already contains the entire machine. A quiz module:

  1. fetches its definition from git (FetchQuizContent(src, ref, path)),
  2. evaluates it (ScoreQuiz),
  3. returns QuizResult{ Passed, QuestionResults[]{ IsCorrect, Feedback } } via POST /api/courses/{slug}/modules/{index}/submit.

A lab check is the same loop with the data source swapped: instead of scoring user-submitted answers against an answer key, it fetches real-world state from an external system and evaluates assertions over it.

Quiz Lab check
FetchQuizContent(src,ref,path) from git fetch lab state from GitLab / Harbor / Nexus
user-submitted answers server-fetched real objects
ScoreQuiz → answer-key comparison policy evaluation over fetched objects
QuizResult{Passed, QuestionResults[]{IsCorrect, Feedback}} CheckResult{Passed, Assertions[]{Passed, Message, Evidence}}
POST /modules/{index}/submit POST /modules/{index}/check

We are not building a new subsystem — we are adding a second evaluator next to ScoreQuiz, and a second fetcher next to the git fetcher.

2. Two-layer separation (the load-bearing idea)

Every check, regardless of backend, reduces to the same shape:

authenticate to a system → fetch the relevant objects → evaluate a predicate over them → return pass/fail + a human-readable reason.

Only the fetch is system-specific. So the design splits hard along that seam:

  • Fetch — typed, per-backend, returns normalized objects. System-specific.
  • Assert — generic predicate evaluation over those objects. Written once.

Conflating the two is what reintroduces per-check code (every new assertion becomes a new code path). Keeping them apart is what gives reach without code.

Why a separate checker-service

It has properties course-service should not grow: privileged provider credentials, Terraform-provider subprocesses, and a policy runtime. It is stateless and knows nothing about courses, users, or git. course-service stays the orchestrator and reuses what it already has (git fetch, progress sink, cooldown tracker).

3. Fetch: Terraform providers as a library

We do not write a provider per backend. We reuse the existing Terraform provider ecosystem.

A Terraform data source is exactly what we need: auth + read + typed output with arguments, and many are list/query shaped (plural). Terraform providers are go-plugin gRPC subprocesses; the protocol exposes GetProviderSchema, Configure, and ReadDataSource. We speak that protocol directly — no .tf files, no terraform binary — exactly as Pulumi's terraform-bridge does to reuse the ecosystem.

So a generic TF-datasource adapter loads any provider binary, configures it with our secrets, calls ReadDataSource with arguments, and gets structured JSON back. Adding a backend becomes configuration, not a new provider:

The contract is the data source name and schema, used directly (e.g. gitlab_project_merge_requests). A provider version change is treated as a maintenance event: re-test every course in dev/stg before promoting. In an airgap with pinned, vendored provider binaries, schema cannot drift under us — it only changes on a deliberate upgrade.

Real grounding — GitLab provider (gitlabhq/terraform-provider-gitlab)

The data sources that cover the canonical labs already exist:

Lab intent Data source Notes
Open a merge request gitlab_project_merge_requests list; server-side target_branch, source_branch, state, author_username filters
Push a commit / branch gitlab_project_branches list branches in project
Commit a specific file gitlab_repository_file / gitlab_repository_tree file existence / content
Push a tag gitlab_project_tags / gitlab_project_tag
MR has approvals gitlab_project_approval_rules
Resolve project (path→id) gitlab_project

gitlab_project_merge_requests schema (abridged, real):

  • Required: project (ID or path) — the injected scope arg.
  • Optional filters (server-side): target_branch, source_branch, state, author_username, author_id, wip, search, scope, …
  • Per-MR (read-only): iid, created_at, author{ username, id, … }, assignee, target_branch, source_branch, state, title, … and more.

This is list-then-filter shaped — exactly right for "did the learner create an MR matching X". author_username being a server-side filter is what lets us double-scope (see §5).

The http provider — escape hatch for uncovered objects

Coverage is per-object. Some things have no data source. Concrete example: there is no personal-access-token data source in the GitLab provider — only project_access_tokens and group_access_tokens. So the "create a PAT" lab cannot use a typed GitLab data source.

For those, the hashicorp/http provider http data source is the fallback:

  • supports method (GET default, also HEAD/POST), request_headers, request_body;
  • returns response_body (string), response_headers, status_code.

So "create a PAT" → GET {gitlab}/api/v4/personal_access_tokens?user_id=…, parse response_body in the policy with json.unmarshal.

Two conditions on the http fallback:

  1. Auth headers are injected by the adapter, not carried in the check spec. The bearer token is a privileged credential; it must never live in policy/spec context (same reason we avoid http.send inside Rego).
  2. http-backed reads couple to the raw API JSON shape, not to a typed provider schema. That is acceptable for a fallback — you simply lose the schema-decoupling benefit for those specific objects. Use it where no data source exists; prefer the typed provider everywhere else.

4. Assert: Rego over input

Rego evaluates a pure function of input — it does not fetch. The adapter fetches, assembles input, then the policy evaluates. (http.send inside Rego is an anti-pattern here: credentials in policy context, untestable, disablable.)

The policy returns a violation set, not a boolean — each violation carries the teaching message:

rego
package lab

# input.objects.merge_requests : normalized MR list from the fetch layer
# input.learner.username       : "knechta", injected server-side

mr_ok(m) {
    m.target_branch == "main"
    m.state == "opened"
    m.author.username == input.learner.username
}

violations[{"msg": "No open merge request targeting `main` was found — check your target branch", "field": "target_branch"}] {
    not any_mr_ok
}

any_mr_ok {
    some i
    mr_ok(input.objects.merge_requests[i])
}

pass := count(violations) == 0

Reference architecture: this is Gatekeeper for learner state instead of admission control — OPA + parameterized policies + CRD-ish delivery. Worth stealing its violations set pattern and shipping a small helper-rule library (mr_exists_targeting(branch), tag_pushed(project), …) so course authors compose readable rules instead of hand-rolling iteration.

Rego vs. flat predicate list: Rego earns its place the moment a check needs real || / nesting ("targets main OR develop", "≥1 MR matching all of these"). A flat predicate list can't express that without becoming a worse Rego.

5. Identity & scope — solved by SSO

All apps (LMS, GitLab, Nexus, Harbor) are SSO-instantiated from a single Keycloak. Therefore knechta in the LMS is knechta in GitLab, Nexus, and Harbor. The username is the join key across every system — there is no mapping layer to build, because SSO already did the binding.

This collapses the previously-open "where does the per-learner scope come from" question to one new field on the JWT claims:

go
type Claims struct {
    Email             string `json:"email"`
    Role              string `json:"role"`
    PreferredUsername string `json:"preferred_username"` // ← NEW: "knechta"
    jwt.RegisteredClaims
}

Populated from the same Keycloak token. knechta then flows LMS session → checker scope → provider read arg with zero lookup.

Three rules that make scope a structural guarantee, not a convention

  1. Identity comes from the token, never the request body. Mirrors the existing SubmitModule, which already takes the learner from claims.Subject. The browser cannot say "check lab1 for someone-else".
  2. Double-scope: project + author. The read is scoped to the learner's own provisioned project (project = "training/knechta/lab1") and author_username = "knechta". The username decides which resource; it is not a filter the spec/policy can widen.
  3. Privileged read, scoped by username — not the learner's own token. The checker authenticates as its own service account (GitLab admin-read token, Harbor robot, Nexus account) and filters to knechta. SSO making knechta exist in GitLab does not mean we use the learner's credential — that breaks the moment a check must inspect something the learner can't see.

One realm assumption to confirm

preferred_username must be immutable in the Keycloak realm. If an admin can rename a user, resources provisioned under the old name orphan and checks silently fail against a path that no longer matches. The platform already keys everything off it, so this is almost certainly already the case — but it is worth a 30-second confirmation (Realm Settings → username not in the editable set) before the first lab ships.

6. Check definition — carried by the lab module, colocated in git

type: lab already exists in the Course CRD enum and in the handlers, but is currently inert — GetModule/GetLab merely expose m.Src as a URL the frontend opens in a tab. That is the insertion point: the lab gains a check: block and a Check button.

A lab's instructions (markdown) and its check definition live in the same git repo / commit — the same colocation the type: modules + index.yaml pattern already provides, fetched through the existing GitCache. Upgrading a check is a normal PR alongside the content it verifies.

yaml
# in a course module index.yaml (git-hosted), or inline in the Course CRD
- name: "Open your first merge request"
  type: lab
  path: courses/git-intro/03-merge-request.md   # instructions (markdown)
  check:
    # FETCH — one or more reads. Names are the TF data source (the contract).
    reads:
      - id: mrs
        provider: gitlab
        instance: gitlab-training            # which configured GitLab
        data_source: gitlab_project_merge_requests
        args:
          project: "training/{{ .Learner.Username }}/git-intro"
          # author_username injected by the adapter, NOT author-supplied
    # ASSERT — Rego, pure function of input. (file beside the markdown)
    policy: courses/git-intro/03-merge-request.rego
    # human-friendly fallback messages keyed by violation field (optional)

CRD vs. git struct

  • No CRD migration. spec.modules[] items carry x-kubernetes-preserve-unknown-fields: true, so a check: block on a module survives the apiserver untouched.
  • Git path needs a Go struct change. FetchModuleIndex currently copies only Name/Type/Src/Ref/Path/Hidden/Prerequisites into Module — a check field in index.yaml is silently dropped today. Add Check to ModuleIndexEntry and Module (Go only, no schema change).

7. Request flow

text
1. Learner clicks "Check" on a lab module.
2. POST /api/courses/{slug}/modules/{index}/check   (Bearer JWT)
3. course-service:
   a. auth + enrollment + prerequisite checks (same as SubmitModule)
   b. cooldown check (reuse CooldownTracker) — rate-limit backend hammering
   c. resolve module → check spec from git (GitCache)
   d. resolve scope: username = claims.PreferredUsername
   e. POST checker-service /evaluate { reads, scope:{username}, policy }
4. checker-service:
   a. for each read: configure provider (warm pool), inject scope args,
      ReadDataSource → normalize → input.objects.*
   b. eval Rego(input) → violations[]
   c. return { passed, assertions[] }
5. course-service:
   a. record via existing recordModuleProgress → user-service
      (a passed lab is just a passed module — no new progress plumbing)
   b. return CheckResult to the frontend

8. Response shape (mirrors QuizResult)

json
{
  "passed": false,
  "assertions": [
    {
      "id": "mr-targets-main",
      "passed": true,
      "message": "Merge request targeting `main` found.",
      "evidence": { "iid": 1, "source_branch": "feature/login" }
    },
    {
      "id": "mr-has-approval",
      "passed": false,
      "message": "Your MR has no approval yet — ask a reviewer to approve it.",
      "evidence": { "approvals_required": 1, "approvals_received": 0 }
    }
  ]
}

The message is the actual teaching surface — it is why we never return a bare ok/ko. evidence is server-observed truth, useful for both the learner and for debugging a check.

9. Worked example — GitLab MR, end to end

03-merge-request.md (learner-facing instructions, git):

markdown
# Open your first merge request
Create a branch `feature/...`, push a commit, then open a merge request
targeting `main`. Click **Check** when done.

03-merge-request.rego (policy, git, beside the markdown):

rego
package lab

mr_targets_main(m) {
    m.target_branch == "main"
    m.state == "opened"
    m.author.username == input.learner.username
}

violations[{"id":"mr-targets-main","msg":"No open MR targeting `main` found."}] {
    not has_mr
}
has_mr { some i; mr_targets_main(input.objects.mrs[i]) }

pass := count(violations) == 0

Fetch (adapter call, conceptually):

text
ReadDataSource(gitlab_project_merge_requests, {
    project:         "training/knechta/git-intro",   # scope (project)
    author_username: "knechta",                       # scope (author), injected
    state:           "opened",
    target_branch:   "main",
})  →  input.objects.mrs = [ { iid, author{username}, target_branch, state, … } ]

Server-side filters narrow the result; Rego confirms existence and binds the author to the session identity. Project + author double-scoping means learner B cannot pass by pointing at learner A's MR.

10. Worked example — PAT via http provider (no data source)

yaml
- name: "Create a personal access token"
  type: lab
  path: courses/git-intro/01-pat.md
  check:
    reads:
      - id: pats
        provider: http
        data_source: http
        args:
          method: GET
          url: "https://gitlab-training/api/v4/personal_access_tokens"
          # request_headers.Authorization injected by the adapter (PRIVATE-TOKEN)
        parse: json          # response_body → JSON for the policy
    policy: courses/git-intro/01-pat.rego
rego
package lab

# input.objects.pats = parsed response_body (array of PAT objects)
own_active_pat(p) {
    p.user_id == input.learner.id        # or filter the API call by user_id
    p.active == true
    p.revoked == false
}
violations[{"id":"pat","msg":"No active personal access token found for your account."}] {
    not has_pat
}
has_pat { some i; own_active_pat(input.objects.pats[i]) }
pass := count(violations) == 0

Note: we check server-observable truth (the token exists, is active, belongs to the learner) and never see the token value. "Clone the repo" has no clean server trace — make it an instruction, not a check; the subsequent push/MR check implicitly proves the clone happened.

11. Integration points in the existing codebase

Minimal, additive surface:

  • middleware.Claims — add PreferredUsername (one field).
  • content.Module / content.ModuleIndexEntry — add Check field.
  • New route — POST /api/courses/{slug}/modules/{index}/check, a structural twin of SubmitModule (auth, enrollment, prerequisites, cooldown, then evaluate + record). Reuse recordModuleProgress verbatim.
  • Reuse CooldownTracker — rate-limit Check clicks so a learner mashing the button doesn't hammer GitLab.
  • Reuse GitCache — resolve the check spec / .rego from git.
  • New checker-service — stateless; TF-datasource adapter + http fallback + Rego engine; holds per-backend service-account secrets (k8s secrets), reaches in-cluster services over DNS, gated by NetworkPolicy.

Nothing about the wire contract depends on whether the platform inlines the check spec or the checker resolves it from git/CRD — same endpoint, decision deferrable.

12. Operational concerns

  • Airgap / pinned providers. Provider binaries are vendored to a known path; the adapter loads from local disk (no registry fetch, faster cold start). Schema cannot drift; it changes only on deliberate upgrade.
  • Golden tests per check. Canned input JSON + expected pass/fail, run in CI against the pinned provider. The "re-test every course on provider bump" step becomes a CI job that names exactly which courses broke — instead of a learner discovering a silently-false check in production. (Rego against a renamed/ missing field evaluates to undefined → assertion silently false; goldens are the cheap insurance.)
  • Provider process lifecycle. Spawn-per-check is sluggish (each provider is a subprocess with a Configure handshake). Prefer a warm pool of configured provider processes, one per (provider, instance/credential set), multiplexing checks. Implementation detail, deferrable.
  • Freshness vs. caching. "Checks upgrade easily" trades against caching the spec/policy from git. Pick the model deliberately: pull-per-check (simple, slow), TTL cache (current GitCache style), or GitOps sync (materialize spec/rego into a ConfigMap/CRD; no live git dependency on the hot path).

13. Build backlog (no architecture left, only build)

  1. Vertical slice — GitLab MR check, end to end (highest leverage first): PreferredUsername claim → /check endpoint → one gitlab_project_merge_requests read via the adapter → one .rego → one golden test. Forces every seam to meet and surfaces whatever this design glossed over before breadth is built.
  2. TF-datasource adapter (go-plugin protocol: schema/configure/read) + warm pool.
  3. http-provider fallback path + JSON parse → input.
  4. Rego helper-rule library for course authors.
  5. Crossplane per-learner provisioning (parallel track — must land before any check can pass, since the checker reads what provisioning stamps out).
  6. Harbor / Nexus reads (verify each needed object has a readable data source; fall back to http where it does not).

14. Open questions (deferrable, don't block the slice)

  • Spec ownership: platform inlines the check spec vs. checker resolves it from mounted config / a CRD. Same endpoint either way.
  • Where Rego lives: inline in CRD / beside the markdown in git / materialized into a ConfigMap by a sync step. (Materialized = colocation and a fast, reliable check path.)
  • Provisioning naming source: convention (training/<user>/lab<N>) vs. Crossplane composed-resource status readback. SSO already fixes the identity; this is only about the resource layout the checker reads back.
